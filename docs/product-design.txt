Multiplayer Video Editor — Product Design Document
1. Product vision
Build a modern, browser-based, multiplayer video editor inspired by the professional workflow and familiarity of DaVinci Resolve, but substantially simpler and designed around collaboration from the beginning.
The easiest description is:
Simplified DaVinci Resolve meets Google Docs/Figma for video editing.
This is not intended initially to compete with Resolve, Premiere, or Final Cut feature-for-feature.
The differentiator is:
Editing together should feel incredible.
A user should immediately see:
who is online
where everyone is in the timeline
what everyone is selecting
what someone is currently changing
who owns a temporarily locked control
where another editor's playhead is
who is presenting
what changed recently
when important project snapshots were created
The interface should feel like a genuinely new generation of creative software rather than a desktop application awkwardly moved into a browser.

3. Architecture concept
The editor is primarily a web application.
There is one central Mac acting as the server.
Initially that machine is:
MacBook Pro M5 Pro / 48 GB RAM
The Mac is effectively our own private cloud.
It will eventually handle:
application hosting
project database
authentication
multiplayer synchronization
original media storage
media uploads
proxy generation
thumbnails
waveform generation
project state
activity history
snapshots
final rendering
exports
We specifically want to avoid depending heavily on paid cloud infrastructure.
Users access the application through a normal browser.

4. Media architecture
Original media lives on the central Mac/server.
Users should not need powerful computers to participate.
This is particularly important because collaborators may be using Macs that are close to ten years old.
The eventual workflow:

Camera Original
      ↓
Upload to server Mac
      ↓
Assign permanent Media ID
      ↓
Generate lightweight editing proxy
      ↓
Browser edits proxy
      ↓
Timeline stores edit decisions
      ↓
Final export uses original media

The browser should not attempt to process giant camera originals when that isn't necessary.
Every media item gets a permanent internal ID.
Projects reference:

MediaAssetId

rather than depending upon:

/SomeFolder/IMG_0384.MOV

Renaming a file should not destroy the project.

For this first UI implementation, simulate these states beautifully.

6. Authentication and users
Keep authentication simple.
The landing experience should eventually support ordinary accounts.

Example:

A user's color becomes part of their identity throughout the editor.
The top-right user control should show:

7. Group model
Keep permissions deliberately simple.
There is essentially one class/group.
Everyone signed into this installation can belong to that group.
When creating a project:

Project Name
Description
Share with Class

Projects can therefore either be personal/private or shared with the class group.
Do not design an enterprise organization-management system.

16. Collaboration colors

22. Property locking
This behavior is extremely important.
Multiple people may select the same clip.
Selection does not lock anything.
However, when someone begins manipulating a specific property, that operation becomes exclusively theirs.
Example:
Kyle clicks into:

Speed: [ 112% ]

Everyone else sees:

Speed: 112%
🔴 Kyle editing

and temporarily cannot change that field.
When Kyle leaves the field, the lock disappears.

23. Clip manipulation locks
Same rule for timeline manipulation.
If Kyle starts dragging a clip:
Kyle owns that manipulation until mouse-up.
Nobody else can simultaneously:
move it
trim it
resize it
Others can still:
inspect it
select it
watch what's happening
Display a tasteful ownership indication.
Do not cover the clip with giant lock icons.

24. Lock failure recovery
Locks cannot get stuck forever.
Eventually locks must automatically release when:
mouse-up occurs
editing finishes
timeout occurs
browser disconnects
user crashes
network connection disappears
The mock state architecture should anticipate this.

25. Real-time property changes
Everything should conceptually update immediately.
For example:
Kyle changes:

Speed
100 → 112

Ashley should see it change almost instantly.
These should eventually be transmitted as tiny project operations rather than whole project files.
Example conceptual operation:

SetClipProperty
Clip: A7B23
Property: Speed
OldValue: 1.0
NewValue: 1.12
User: Kyle

Build the application's state architecture around this concept even though networking does not need to work yet.

26. Personal undo
Undo is per person.
If Kyle presses Command-Z:
Kyle undoes Kyle's latest eligible action.
He does NOT undo Ashley's last edit simply because it happened most recently.
This distinction is fundamental.
Do not design a conventional single-user global undo stack.

27. Autosave
There should essentially be no Save button for normal editing.
Project edits continuously save.
Eventually:

Saving…

becomes:

Saved

Show this subtly somewhere in the top toolbar.
Users should trust that their work exists.

32. Color philosophy
Color science must eventually be treated as mathematically serious.
Do not invent approximate color math.
The eventual product should:
understand camera log footage
detect/choose the camera input color profile
convert footage into a consistent high-quality internal working color space
perform grading there
correctly transform to the display/output color space
preserve color precision through the pipeline
The exact implementation can be designed later using proven color-management technology.
For the UI prototype, build all controls but do not pretend fake math is production color science.

33. Simplified node system
Keep the professional node idea because it is extremely powerful and educational.

34. AI-assisted grading
This is one of the most exciting future features.
A user can say:
"Make this warmer and more cinematic but keep the skin natural."
AI should not merely apply a hidden preset.
Instead it should construct actual editable grading nodes.
For example:

Balance
Temperature +350

Contrast
Contrast 1.12
Pivot .47

Skin
Saturation -4%

Look
Warm highlights
Cool shadows

Then AI can explain:
"I corrected the white balance first, increased contrast slightly, preserved the skin tones, and added a subtle warm-highlight/cool-shadow look."
This means AI becomes a teacher as well as an editor.
The UI should anticipate this feature now.

45. Motion design
Animation is part of the product.
But motion should communicate state.
Examples:
Someone selects a clip
Colored outline eases into view.
Someone starts modifying a property
Inspector edge gets a soft color glow.
Someone moves a clip
Remote clients see it glide into place.
Collaborator joins
Their avatar appears smoothly.
Live playback starts
A LIVE badge transitions into view.
Panel opens
It slides/fades naturally.
Snapshot saved
History item expands briefly and settles into place.
Render completes
Progress resolves elegantly into a success state.

46. Performance rule
Do not make "modern" mean "GPU-melting."
Remember:
Some collaborators have old MacBooks.
Animations should heavily favor:
transform
opacity
composited animations
Avoid covering the entire application in expensive animated blur effects.
The target is:
Beautiful at 60 FPS on modest hardware.
Also respect operating-system Reduced Motion preferences.
